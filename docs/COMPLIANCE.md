# Compliance mapping template

This document maps the engineering controls *implemented* in `sagp` to named clauses in GDPR, the HIPAA
Security and Privacy Rules, and NIST SP 800-53 Rev. 5. It exists so that a reviewer can see, per control,
exactly what the code does and exactly what it does not do. Most controls below are now built — see §1 for
status and the load-bearing caveats.

## 2. How to read this document

Every mapping table below has the same four columns.

| Column | Meaning |
|---|---|
| **Control** | The clause identifier, verbatim from the source instrument. |
| **What it requires** | A short, neutral paraphrase of the obligation. Not the legal text. Read the instrument. |
| **What this system implements** | Concrete, checkable engineering facts: a module path, an HTTP status, a config key, a numbered stage from the C0–C26 request path in [Architecture](ARCHITECTURE.md). If a row cannot name an artefact, it says so. |
| **Gap / operator responsibility** | What is missing, what is only partial, and what the deploying organisation must supply. This column is never empty. |

**No row in this document is marked "compliant."** That word does not appear as a status anywhere below.
A control is either implemented in code, partially implemented, or not implemented — and even a fully
implemented technical control does not by itself satisfy an obligation that also has organisational,
contractual, and documentary components.

Detection-coverage markers used in the HIPAA identifier table (§4.1):

| Marker | Meaning |
|---|---|
| ✅ | A dedicated recognizer is configured and its decision is deterministic or validated — a checksum, a format validator, or a library lookup. Not a claim of 100% recall. |
| ⚠️ | Detected only probabilistically (NER), only in some formats or locales, or only above a score threshold that a reviewer must consider. |
| ❌ | The identifier passes through unmasked. Either no recognizer is configured, or the entity sits under `allow:` in the canonical entity policy — detected and audited, but never substituted. |

> **The recall figures in §4.1 are build-gate targets checked against a real run, not coverage claims.**
> `docs/metrics/latest.json` exists and M6 measured EMAIL_ADDRESS / CREDIT_CARD / IN_AADHAAR / PERSON recall
> at **1.0** on a small synthetic set ([Guardrails](GUARDRAILS.md) §10.2) — those clear their floors. A ✅
> still means only that a recognizer is *configured* in the canonical entity policy
> ([Guardrails](GUARDRAILS.md) §8.2); it is **not** a real-world coverage result, and no number in §4.1 may
> be excerpted as detection coverage. Presidio detection is best-effort and never 100%.

**Change control.** [CLAUDE.md](../CLAUDE.md) §8 requires that adding any guardrail signal is a
single commit containing three edits: an `AuditEvent` field, a row in *this* document, and a case in
`tests/unit/test_audit_no_pii.py`. (That is a change-control rule in CLAUDE.md §8, not one of the 13
numbered invariants in CLAUDE.md §2.) If a control appears in code and not here, that is a process failure.

## 3. GDPR (Regulation (EU) 2016/679)

| Control | What it requires | What this system implements | Gap / operator responsibility |
|---|---|---|---|
| **Art. 5(1)(c)** — data minimisation | Personal data must be adequate, relevant, and limited to what is necessary. | The prompt that reaches the LLM contains placeholders, not identifiers: stages C11–C12 resolve PERSON aliases and anonymize through the `VaultPlaceholder` operator, producing `<PERSON_1>`-style tokens. Retrieved chunks are masked into the *same* request vault at C17. Client responses carry no scores, no entity types, and no counts (reconciliation ledger row 13) — `GuardrailReport` and `X-PII-Masked-Count` were removed from the response body. Audit records store HMAC tokens, never raw values, enforced by `audit/scrub.py` and a closed `AuditEvent` schema (`extra="forbid"`). | Minimisation at *ingest* is not implemented. `ingest_mode=raw` stores full chunk text including identifiers (see the pseudonymisation row). The operator decides what goes into `data/private/` — there is no upstream filter. Masking recall is not 100% (see [Guardrails](GUARDRAILS.md) §11). |
| **Art. 4(5) + Art. 32(1)(a)** — pseudonymisation | Process personal data so it can no longer be attributed to a data subject without separately-kept additional information, and keep that additional information subject to technical and organisational measures. | The vault is request-scoped, in-memory, and cleared in a `finally:` block at C26. It is never persisted, never written to disk, and never survives a request — so there is no long-lived re-identification table to steal. Placeholders are per-request ordinals derived from nothing about the value. Rehydration (C23) requires the `pii:reveal` scope **and** `SAGP_REHYDRATE_OUTPUT=1`; unknown placeholders are left verbatim rather than resolved through any global map. | **The shipped default is `ingest_mode=raw`. Masking happens at RETRIEVAL, not at ingest. The vector store at `data/qdrant/` holds raw personal data in the chunk payload.** This is a deliberate, documented decision (ADR-0006, reconciliation ledger row 11): masking at ingest collides placeholders across identities and destroys retrieval, because queries are raw and the corpus would be masked. **The compensating controls are loopback binding, filesystem permissions, and FileVault full-disk encryption — not the guardrail.** Copying `data/qdrant/` off the box leaks the corpus with no control in the path ([Limitations](LIMITATIONS.md) item 11). Additionally: the vault is not scrubbed from the heap — Python strings are immutable, so a core dump or a memory scraper recovers the mapping. Set `ulimit -c 0` and do not co-locate untrusted processes. |
| **Art. 4(5)** — the additional information | The re-identification key must be kept separately and protected. | The audit log stores `HMAC(key, f"entity:{type}\x1f{normalize(type,value)}")` rather than raw values, so two occurrences of the same identifier are linkable across records without the value being recoverable from the log alone. Key and pepper are generated at `scripts/provision/09_secrets.py` with mode `0600`. | **The HMAC pepper is a key of the same sensitivity as the data it protects.** Identifier spaces such as US SSN (10⁹), Aadhaar (10¹²), and national phone-number ranges are small enough to brute-force offline if the pepper is disclosed. Treat pepper compromise as a data breach of every value ever tokenised under it. Custody, escrow, and rotation are the operator's responsibility — see [Operations](OPERATIONS.md). |
| **Art. 25** — data protection by design and by default | Technical and organisational measures implementing the principles, by design and by default. | Fail-closed is the only fail mode: [CLAUDE.md](../CLAUDE.md) invariants 3 (never bypass the guardrail pipeline) and 6 (fail-CLOSED) forbid any `*_FAIL_MODE=open` or `*_DISABLED` env var, and dev bypasses live in a separate app factory the production factory cannot import. Guardrails run as FastAPI dependencies, never `BaseHTTPMiddleware`, so typed 400s cannot degrade into opaque 500s. Thresholds are data in `config/guardrails.yaml` and `config/entities.yaml`, validated `0.0 < t <= 1.0` at startup — a typo'd env var refuses to boot rather than silently defaulting. The config hash is written into every audit record. Every guardrail block returns HTTP 400 with an identical opaque body and is padded to a fixed rejection deadline (a placeholder 120 ms, calibrated above the slowest detector at M13 — not a per-detector minimum), so the rejection surface is not a detector oracle. | "By design" here covers the request path only. It does not cover the organisational half of Art. 25 — retention policy, access review, purpose limitation, and DPIA are outside this repo (§7). |
| **Art. 30** — records of processing activities | Maintain a record of processing activities under your responsibility. | Every request writes an append-only, hash-chained `AuditEvent` (JSONL, `fsync`, mode `0600`, daily rotation with a carry-over record) recording request ID, principal ID, per-stage decisions and timings, the `guardrails.yaml` hash, the system-prompt sha256, and both `completion_pre_rehydrate_sha256` and `completion_returned_sha256`. `make audit-verify` walks the chain and exits non-zero on any break. | An audit log is **not** an Art. 30 record. Art. 30 requires a documented register of processing purposes, categories of data subjects and data, recipients, transfers, retention periods, and security measures — a document maintained by the controller, not a log emitted by an application. This repo produces evidence that can be cited in such a register. It does not produce the register. |
| **Art. 33 / Art. 34** — breach notification | Notify the supervisory authority within 72 hours of becoming aware; notify data subjects when the risk is high. | Detection inputs exist: `verify_chain()` detects audit tampering and reports `first_bad_seq`; `manifest.verify(mode="full")` at every boot detects any change under `models/`; the egress guard records `python_egress_attempts_blocked`; high-severity alarms fire on tag/bidi characters in ingested pages (I4), on placeholder injection in retrieved chunks (C16), and on any `scrub_violation`. | **No incident response plan, no notification workflow, no clock, and no defined "aware" trigger exist in this repo.** Nothing pages anybody. Nothing escalates. The 72-hour clock is an organisational obligation with named owners and a rehearsed runbook — see §7. Note also that audit timestamps are local-clock ([Limitations](LIMITATIONS.md) item 6), so the log cannot by itself establish *when* awareness began to a third party. |
| **Art. 44–49** — international transfers | Personal data may only be transferred to a third country or international organisation under an adequacy decision, appropriate safeguards, or a derogation. | **An air-gapped architecture is a genuinely favourable starting point for the transfer question — and what has been tested is a demonstration, not a proof.** A sealed host is *designed* to make no outbound connection: there is no cloud LLM API, no telemetry, no model download at request time, and no vendor analytics; the runtime venv contains no `huggingface-hub`, and [CLAUDE.md](../CLAUDE.md) invariant 2 permits exactly two destinations, both loopback — `127.0.0.1:11434` (Ollama) and `127.0.0.1:6333/6334` (Qdrant, demo profile). The evidence is a demonstration, not a proof. `make verify-online` establishes a negative control while the host demonstrably has internet, then re-runs the identical probes under `SAGP_GUARD=enforce` and requires `EgressViolation` from each; `make verify` runs nine offline assertions, each paired with a positive control. **Both have run (M13):** the online control completed a real TCP handshake to `1.1.1.1:443` in **6.58 ms** unguarded and then raised `EgressViolation` under enforce, and all nine offline assertions pass. The claim available is narrow and must be stated in exactly this form: *the Python-level egress guard refused every probe that was constructed, each paired with a negative control.* It is not a claim that the host cannot transfer data. Three exclusions are load-bearing and belong here rather than only in the gap column. (1) The controls are software, not physics: the host retains a Wi-Fi radio, Thunderbolt/Ethernet, Bluetooth, and USB NIC support ([Limitations](LIMITATIONS.md) item 1). (2) Native code is outside the Python guard entirely — `grpcio`'s C core, ONNX Runtime, and anything reached via `ctypes` can call `connect(2)` without entering CPython's socket layer or emitting a PEP 578 event ([Limitations](LIMITATIONS.md) item 2). (3) Ollama and the Docker daemon are sibling processes outside both guard layers ([Limitations](LIMITATIONS.md) item 3). What this row offers is evidence in support of a transfer assessment somebody else performs. | Only the optional `make seal-pf` anchor closes the native-code category, and only for UID-owned TCP/UDP; it does not cover Docker, whose traffic leaves via a root-owned VM interface. Physical media control and personnel policy carry the rest — §7 items 1 and 2. **Do not restate this row as "makes no outbound connection at all" or "cannot transfer data anywhere."** Neither is supportable, and both are what get lifted into a slide. The Docker path is **NOT isolated by compose network options** — `make spike-docker` (run 2026-08-01) resolved OQ-4/OQ-5 negatively (§5, SC-7); its egress control comes from `make seal-pf` + loopback, and DNS leaks via the embedded resolver. Never call it "isolated". |
| **Art. 17** — right to erasure | Erase personal data without undue delay on request, where a ground applies. | Document-level deletion works and is exercised on every ingest: I10 deletes all points for a superseded `doc_sha256` before upserting, and point IDs are `uuid5(NS, f"{sha}:{idx}")`, so deletion by source document is deterministic and complete within the vector store. | **Per-data-subject erasure is not implemented and is not straightforward.** You can delete a *document*; you cannot ask this system to delete *every trace of Alice*. Because `ingest_mode=raw` stores unmasked chunk text, satisfying an erasure request means locating and re-ingesting every source document mentioning the subject. In the audit log, erasure is approximated rather than performed: rotating the PII pepper renders all previously written HMAC tokens permanently unlinkable, which is the only erasure primitive the log has. Backups are outside this repo entirely and are frequently where erasure requests actually fail. |
| **Art. 32(1)(b)** — confidentiality, integrity, availability, resilience | Ensure ongoing CIA and resilience of processing systems. | Integrity: full manifest verification at every boot (never `quick` mode — reconciliation ledger row 23), hash-chained audit, Ed25519 signature over `MANIFEST.json`. Confidentiality: loopback-only binding, `0600`/`0700` modes, bearer-token auth on every route. | Availability and resilience are weak by design on this hardware. Denial of service by resource exhaustion is largely unmitigated on 8 GB: a concurrent burst OOMs before rate limits bite, and `uvicorn --workers 1` plus `anyio.CapacityLimiter(2)` is the whole defence ([Limitations](LIMITATIONS.md) item 17). Backup and restore are documented in [Operations](OPERATIONS.md) §5 as manual cold-backup procedures — there is no automated backup/restore feature. |
| **Art. 35** — data protection impact assessment | Carry out a DPIA where processing is likely to result in a high risk. | Nothing. This repo does not perform, template, or prompt for a DPIA. | A DPIA is very likely **required** for a realistic deployment of this system: it combines new technology, systematic processing, and — in the intended enclave use case — special-category or large-scale personal data. It is a controller obligation with a defined structure (Art. 35(7)). See §7. |

## 4. HIPAA (45 CFR Parts 160 and 164)

### 4.1 Safe Harbor — all 18 identifier categories under §164.514(b)(2)

Marker legend is in §2. "Recognizer" refers to a Presidio recognizer registered by
`src/sagp/guardrails/presidio_factory.py` and `src/sagp/guardrails/recognizers.py`, or a custom
`PatternRecognizer` defined under `config/recognizers/`.

| # | §164.514(b)(2)(i) category | Cov. | What actually happens |
|---|---|---|---|
| 1 | Names | ⚠️ | `PERSON` via spaCy `en_core_web_md` 3.8.0 NER. Thresholds 0.50 ingress / 0.35 egress. Alias resolution at C11 is longest-first, strict-subset, same-origin only; ambiguity mints a fresh placeholder rather than cross-linking. Probabilistic. Metrics floor `PERSON ≥ 0.80`; M6 measured PERSON recall **1.0** on the small Latin-script eval subset (a build gate cleared, not a coverage result). **OPEN QUESTION — OQ-9:** spaCy publishes only aggregate `ENTS_F` (md 84.73), never per-label PERSON F, and OntoNotes is US/Western-news weighted. PERSON recall on Indian names is unmeasured. No recall floor is asserted for Devanagari or transliterated names. |
| 2 | Geographic subdivisions smaller than a state | ⚠️ | `LOCATION` via NER, thresholds 0.55 / 0.40. Catches many city and region mentions. **No ZIP-code recognizer is configured**, so postal codes and equivalent geocodes are not detected (❌ for that sub-element). The Safe Harbor three-digit-ZIP rule and its 20,000-population test are not implemented in any form. Street addresses are detected only insofar as NER tags their components. |
| 3 | All elements of dates except year, and ages over 89 | ❌ | **`DATE_TIME` is an `allow` entity in the canonical `config/entities.yaml` ([Guardrails](GUARDRAILS.md) §8.2, [Architecture](ARCHITECTURE.md) §8.3): detected and audited, but NEVER masked — on ingress or on egress.** The ingress score threshold of **0.85** is deliberately high and the egress threshold is `off`, but neither drives a substitution: a date that clears the threshold produces a type-and-count entry in the audit record and is left verbatim in the prompt, the context, and the model output. Masking dates was judged to destroy the answer to most handbook questions. There is no age extraction and no age-over-89 rule anywhere. Admission, discharge, and death dates are handled exactly like any other date, which is to say not removed at all. |
| 4 | Telephone numbers | ✅ | `PHONE_NUMBER` via `phonenumbers==9.0.35`, thresholds 0.50 / 0.40. Library-validated, region-dependent. Unusual local formats and extensions may be missed. **No recall floor is asserted and no recall has been measured (target, unmeasured — see §2).** |

Metrics floor `EMAIL_ADDRESS ≥ 0.98`; M6 measured recall **1.0** on the eval set — a build gate cleared, not a real-world coverage result. |

It remains in the source file under `data/private/`, which is the operator's to protect. |
| 18 | Any other unique identifying number, characteristic, or code | ❌ | Unbounded by definition, therefore not satisfiable by a fixed recognizer set. The repo ships custom `EMPLOYEE_ID` (with check digit), `PROJECT_CODENAME` (deny list), `API_KEY` and `PRIVATE_KEY` (pattern plus entropy gate) recognizers as worked examples of how a site extends this category — not as coverage of it. |

Two identifier classes outside Safe Harbor's US framing are also handled and are worth naming for
non-US deployments: `IN_AADHAAR` (Verhoeff checksum, binary, BLOCK-listed, metrics floor ≥ 0.95; M6
measured recall **1.0** on the eval set — a build gate cleared, not real-world coverage) and `IN_PAN`
(thresholds 0.50 / 0.40; no recall floor asserted, none measured — **unmeasured**).

### 4.2 This system does not de-identify PHI

> **This system does NOT achieve HIPAA Safe Harbor de-identification under §164.514(b)(2), and output
> from it must not be treated as de-identified.**

The reasons, stated plainly:

1. **Coverage is incomplete.** Eight of the eighteen categories — medical record numbers, health plan
   beneficiary numbers, vehicle identifiers, device identifiers, IP addresses, biometric identifiers,
   full-face photographs, and the open-ended "any other unique identifying number" — have **no recognizer
   at all**, and web URLs are detected by nothing (row 14 is covered structurally, not by detection).
   Safe Harbor requires removal of all eighteen. Partial removal is not partial Safe Harbor; it is not
   Safe Harbor.
2. **The detectors that do exist are probabilistic.** Names and geographic subdivisions depend on spaCy
   NER over a model trained on Western news text, with per-label recall for the target population
   unmeasured (OQ-9). A threshold is a dial between missing PHI and destroying utility. There is no
   setting at which it stops being a dial.
3. **Date handling does not meet the rule.** `DATE_TIME` is an `allow` entity — **detected and audited but
   never masked, on either surface** — and no age-over-89 aggregation exists.
4. **No expert determination has been performed.** §164.514(b)(1) — the alternative route to
   de-identification — requires a person with appropriate knowledge and experience applying generally
   accepted statistical and scientific principles, documenting the methods and results, and concluding the
   re-identification risk is very small. Nothing of the kind has happened here. This document is not that
   determination and cannot substitute for one.
5. **The stored corpus is not de-identified in any sense.** `ingest_mode=raw` means the vector store holds
   the original text. Masking applies to what reaches the model and what reaches the caller — not to what
   is at rest.
6. **Safe Harbor also requires the absence of actual knowledge** that residual information could identify
   an individual. That is a factual determination about your data and your recipients. Software cannot
   make it.

Treat every output of this system as PHI. Apply the full Privacy and Security Rules to it.

### 4.3 Security Rule — technical safeguards

| Control | What it requires | What this system implements | Gap / operator responsibility |
|---|---|---|---|
| **§164.312(b)** — Audit controls | Hardware, software, or procedural mechanisms that record and examine activity in systems containing or using ePHI. | Append-only JSONL at `audit/events-YYYYMMDD.jsonl`, mode `0600` inside a `0700` directory, `fsync` per record, daily rotation with a carry-over record linking chains across files. `AuditEvent` is frozen with `extra="forbid"` — an undeclared field is a hard error, not a silent write. Records carry request ID, principal ID, per-stage decision and timing, `guardrails.yaml` hash, system-prompt sha256, HMAC entity tokens, and the incident ID that a 400 response returns. `audit/scrub.py` asserts no raw values ever reach the sink and raises a loud alarm plus a `scrub_violation` record if one does. C25 makes an audit write failure fail the *request*: a 503 is returned and the response is withheld. `make audit-verify` walks the hash chain and reports `first_bad_seq`. | **Recording is implemented; examining is not.** There is no alerting, no SIEM forwarding, no scheduled review, and no dashboard. Nobody is notified of anything. The daily off-box export of the ledger head digest — the step that makes the chain meaningful against an attacker with write access — is a **manual** operator step (`make audit-verify` prints the head digest; recording it off-box is documented in [Operations](OPERATIONS.md) §2, not automated). Timestamps are local-clock. Retention deletion is a documented manual procedure ([Operations](OPERATIONS.md) §3); there is no automated sweep. |
| **§164.312(a)(1)** — Access control | Technical policies and procedures allowing access only to those persons or software programs granted rights. | Two bearer tokens generated at provision: `SAGP_API_TOKEN` with scopes `chat` and `ingest`, and `SAGP_API_TOKEN_REVEAL` which adds `pii:reveal`. Every route depends on `get_principal()`; a missing or invalid token returns 401 with a generic body. Rehydration of real values at C23 requires both the `pii:reveal` scope and `SAGP_REHYDRATE_OUTPUT=1`. Rate limiting is per `principal.id`. All listeners bind `127.0.0.1` only. Filesystem modes are `0600` for secrets and audit records, `0700` for the audit directory. | **§164.312(a)(2)(i) unique user identification is NOT satisfied.** These are *shared, role-shaped* tokens, not user identities. The audit log records which token was used, never which human. Two people holding the same token are indistinguishable in every record this system writes. **§164.312(a)(2)(ii) emergency access** — no break-glass procedure. **§164.312(a)(2)(iii) automatic logoff** — tokens do not expire and there is no session concept. **§164.312(a)(2)(iv) encryption/decryption** (addressable) — FileVault full-disk only; see §164.312(e) below. Rehydration returns real PHI to a caller authenticated by a shared token over plaintext loopback with no user identity, no RBAC, and no TLS ([Limitations](LIMITATIONS.md) item 14). That is defensible for a single-tenant sealed box and inadequate for anything else. |
| **§164.312(e)(1)** — Transmission security | Technical measures to guard against unauthorised access to ePHI transmitted over an electronic communications network. | ePHI is not transmitted off-host by any path **this repository controls**. All application traffic is loopback — the API on `127.0.0.1`, Ollama on `127.0.0.1:11434`, Qdrant on `127.0.0.1:6333/6334` in the demo profile. The Python egress guard refuses non-loopback destinations at two layers; that refusal was demonstrated against a paired negative control (`make verify-online`) at **M13** — a real handshake to `1.1.1.1:443` unguarded, `EgressViolation` under enforce. Nothing here is *proven*; the strongest claim available is "the guard refused each probe that was constructed, against a paired negative control" (§3, Art. 44–49 row). **"ePHI is not transmitted over any network" is not a claim this system can support**: Ollama, the Docker daemon and native extensions (`grpcio`'s C core, ONNX Runtime, `ctypes`) sit outside both guard layers ([Limitations](LIMITATIONS.md) items 2–3). AF_UNIX is deny-by-default with an empty allowlist, and `/var/run/docker.sock` is denied unconditionally in OPERATE. | **There is no TLS anywhere.** The API speaks plaintext HTTP and the bearer token travels in a plaintext `Authorization` header. This is acceptable only on the assumption that the traffic never leaves the host — an assumption resting on loopback binding plus a demonstration (M13), not on a verified property. And even granting it, any local process with sufficient privilege can capture the loopback interface. **§164.312(e)(2)(i) integrity controls** (addressable) — no per-message integrity check beyond what the loopback path implies. **§164.312(e)(2)(ii) encryption** (addressable) — not implemented. **Any deployment that exposes this API beyond `127.0.0.1` must add TLS with client certificates or an equivalent, and must revisit the entire access-control row above before doing so.** |

Administrative safeguards (§164.308), physical safeguards (§164.310), organisational requirements
(§164.314, business associate contracts), and documentation requirements (§164.316) are **entirely
outside this repository**. See §7.

Control titles are from the Rev. 5 catalogue. No baseline (Low/Moderate/High) is claimed, no

| **AC-4** Information Flow Enforcement | Enforce approved authorisations for controlling information flow within the system and between connected systems. | The air gap is the flow control. `netguard/egress.py` runs two layers: an L1 monkeypatch over `socket`, and an L2 PEP 578 audit hook that fires at C level and is intended to catch `_socket.socket().connect()`, which bypasses L1 by construction; L2 catches it (verified at M11, CLAUDE.md invariant 2). C22d range-checks `[Sn, p.X]` citation markers against the blocks and pages actually supplied. | **AU-10** Non-repudiation | Protect against an individual falsely denying having performed an action. | Ed25519 signatures over `MANIFEST.json` and each `EVIDENCE-*.json`; a hash-chained evidence ledger; per-request hash chaining in the audit log. | **This control is NOT satisfied and non-repudiation is NOT claimed.** Three independent reasons, any one of which is sufficient. them must be replaced by a period your counsel sets against your jurisdiction, your sector, and your
contracts. Where the GDPR and HIPAA columns pull in opposite directions, that tension is real and is called
out rather than resolved.

|---|---|---|---|---|---|
| **Audit log** | `audit/events-YYYYMMDD.jsonl`, mode 0600 | **6 years** (ESTIMATE — operator must set) | Art. 5(1)(e) storage limitation argues for the shortest useful period; Art. 5(2) accountability and Art. 32 argue for keeping enough to demonstrate the controls worked. The record contains no raw personal data by construction — only HMAC entity tokens — so the storage-limitation pressure is weaker here than for any other class. | §164.316(b)(2)(i) requires retention of required documentation for six years from creation or last effective date. ## 7. Controls you must add outside this repo

Everything below is required for a real deployment and **none of it is, or could be, in this repository**.
A technical control with no organisation around it is a demo.

1. **Physical security.** This system's isolation assumption is that nobody walks up to the machine.
   Controlled premises, locked enclosure, visitor logging, and a policy on portable media —
   [Limitations](LIMITATIONS.md) item 1 is explicit that the host keeps its Wi-Fi radio, Thunderbolt,
   Bluetooth, and USB NIC support. HIPAA §164.310 is the relevant clause set; NIST PE-2, PE-3, PE-6, MP-2,
   and MP-6 are the relevant families. Include media sanitisation for the SSD at decommissioning
   (NIST SP 800-88).
2. **Personnel screening and workforce controls.** The threat model assumes a *cooperative* operator and a
   possibly-hostile dependency or document. A hostile operator defeats this system trivially. Background
   screening, role definition, a sanctions policy, termination procedures, and — for a high-value enclave —
   two-person integrity for provisioning and unsealing. HIPAA §164.308(a)(3) and (a)(5); NIST PS-3, PS-4,
   PS-7, AC-5.
3. **Contracts: BAAs and DPAs.** If PHI is processed, a Business Associate Agreement is required with every
   business associate (HIPAA §164.502(e), §164.314(a)). If personal data is processed on another
   controller's behalf, an Art. 28 processor agreement is required. Note the honest advantage here: an
   air-gapped system has an unusually short vendor list — but "unusually short" is not "empty," and the
   organisation running the machine is still a party.
4. **Incident response plan.** Named owners, a defined "aware" trigger for the Art. 33 seventy-two-hour
   clock, escalation paths, notification templates, and rehearsals. This repo *detects* several classes of
   incident — chain break, manifest mismatch, egress attempt, scrub violation, poisoned document — and
   *notifies nobody*. HIPAA §164.308(a)(6); NIST IR-4, IR-6, IR-8.
5. **Lawful basis for processing.** GDPR Art. 6, and Art. 9 if special-category data — which health data
   in a HIPAA-shaped deployment is by definition. Identify it before the first ingest, document it, and
   make sure it covers the LLM processing specifically, not merely the storage of the source documents.
6. **DPIA.** GDPR Art. 35, with the structure required by Art. 35(7). Almost certainly required here: new
   technology, systematic processing, and likely special-category or large-scale data. Consult the
   supervisory authority under Art. 36 if the residual risk stays high.
7. **Records of processing activities.** GDPR Art. 30 — a maintained register, not a log file. See the
   Art. 30 row in §3.
8. **Backup encryption at rest beyond FileVault.** FileVault protects a powered-off disk and nothing on a
   running, unlocked one. Backups leave the machine and inherit the raw personal data in the vector store.
   Encrypt them independently, with keys held separately from the backup media, and **test restore**.
   NIST CP-9(8), SC-28(1).
9. **Key custody.** Five secrets are generated by `scripts/provision/09_secrets.py`: the two API bearer
   tokens, the audit HMAC key, the PII pepper, and the Ed25519 signing key. Every one is `0600` on the
   same disk as the data it protects. Define custody, escrow, split knowledge, rotation cadence, and
   rotation *effect* for each (the pepper's rotation effect — permanently breaking linkability of old
   tokens — is a feature, and it is also irreversible). Consider an HSM or smartcard for the signing key;
   until then, [Limitations](LIMITATIONS.md) item 5 applies in full. NIST SC-12, SC-17, IA-5.
10. **Third-party audit.** Nothing in this repo has been independently assessed. If an assurance claim is
    going to be made to a customer, a regulator, or an insurer, it must come from an assessor, not from
    this file. Budget for it, and expect the assessor to start with §4.2 and §5's AU-10 and RA-5 rows.
11. **Model licence compliance.** `llama3.2` is distributed under the Llama 3.2 Community Licence, which is
    **not** an OSI-approved open-source licence, carries an Acceptable Use Policy, and imposes a condition
    on entities exceeding 700 million monthly active users. Legal must review it against your intended use
    before deployment. See [THIRD_PARTY_LICENSES.md](../THIRD_PARTY_LICENSES.md).
12. **Training and awareness.** Operators need to know what `PROMPT_REJECTED` means, why `ingest_mode=raw`
    makes `data/qdrant/` sensitive, why a backup to an unencrypted drive is a breach, and why the ledger
    head digest gets exported every day. HIPAA §164.308(a)(5); NIST AT-2, AT-3.
